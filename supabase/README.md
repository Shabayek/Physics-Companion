# Supabase backend

Online features (leaderboard; cloud save in Phase 7) use [Supabase](https://supabase.com). Everything is
optional: without configuration the game runs fully offline and the leaderboard shows your personal
best runs on the device.

## Setup (about 10 minutes)

1. **Create a project** at <https://supabase.com> (the free tier is enough).
2. **Enable anonymous sign-ins:** *Authentication → Sign In / Providers → Allow anonymous sign-ins*.
   Players never enter an email; each browser gets an anonymous account.
3. **Run the migrations:** open *SQL Editor*, paste each file from `supabase/migrations/` in name order
   and run it. (With the Supabase CLI: `supabase link` then `supabase db push`.) The migrations are
   idempotent — running them twice is safe.
4. **Configure the app:** *Project Settings → API* → copy the *Project URL* and the *anon public* key into
   `.env.local` (see `.env.example`):

   ```bash
   VITE_SUPABASE_URL=https://YOUR-PROJECT.supabase.co
   VITE_SUPABASE_ANON_KEY=eyJ...
   ```

5. **Email links (cloud save across devices):** *Authentication → URL Configuration* → set the *Site URL*
   to where the game is hosted (e.g. `https://physics.example.com`) and add `<site>/profile` to the
   *Redirect URLs* (for local development also `http://localhost:5173/profile`). The *Email* provider must
   be enabled (it is by default). For production, configure a custom SMTP sender under
   *Authentication → Emails* — Supabase's built-in sender is rate-limited and meant for testing.
6. Restart `npm run dev`. *Settings → Online features* should say `Online (YOUR-PROJECT.supabase.co)`.

The anon key is meant to be public; all protection comes from row-level security and the validated
database functions below.

### Recommended hardening

- *Authentication → Rate Limits*: keep the anonymous sign-in rate limit low (e.g. 30/hour per IP).
- *Authentication → Attack Protection*: enable CAPTCHA for sign-ups if you see abuse.
- Anonymous accounts that never joined the leaderboard can be cleaned up periodically (run as an admin
  in the SQL editor):

  ```sql
  delete from auth.users u
  where u.is_anonymous and u.created_at < now() - interval '30 days'
    and not exists (select 1 from public.profiles p where p.id = u.id);
  ```

## What the database enforces

- Tables cannot be written directly (privileges revoked, RLS without write policies). Players can read
  only their own rows; public boards come from `get_leaderboard()`.
- `submit_score()` validates every submission: signed-in player with a profile, known board, answer log
  consistent with the claimed results, no humanly impossible answer times, per-mode limits (score per
  answer, Blitz clock incl. hint penalties, Sprint/Survival/boss rules, daily date window and one entry
  per day and tier), retry de-duplication, and 10 submissions per minute.
- Display names: 3–24 safe characters, unique (case-insensitive), word blocklist; Kid mode accepts only
  generated nicknames ("Quantum Otter 42").
- `delete_my_data()` removes the player's profile, scores and cloud save.
- Cloud saves (`cloud_saves`, one per player) are private; `put_cloud_save()` uses optimistic concurrency
  (expected revision → `conflict` with the current save), limits saves to 256 KB and one write per 2 s.

## Cloud save and devices

- Cloud save is opt-in (Profile → Cloud save). The player is signed in anonymously; the save belongs to
  that anonymous account.
- To use the same progress on another device, the player links an email (Supabase turns the anonymous
  account into a permanent one after the emailed confirmation link), then uses *Sign in with email* on
  the other device (magic link, no password). In Kid mode both actions sit behind a parental gate.
- Devices merge automatically (three-way merge against the last synced version): counters such as Quanta
  add up, best results are kept, collections and achievements are combined.
- When a device signs in to an account, its previous anonymous account's leaderboard profile stays on
  the server; it can be removed with *Delete my online data* before signing in, or by the cleanup query.

**Limitation:** questions are generated by the game client, so the database checks plausibility rather
than re-grading answers. Each run's seed and answer log are stored, so a future Edge Function can re-grade
runs with the same TypeScript engine.

## Tests

`npm run test:db` starts a throwaway local PostgreSQL (no Docker needed), emulates the Supabase roles and
`auth.uid()` (`tests/supabase_shim.sql`), applies the migrations twice and runs `tests/*.test.sql`.
A unit test (`tests/leaderboard-contract.test.ts`) checks that the SQL's constants, word lists and function
signatures match the client.
